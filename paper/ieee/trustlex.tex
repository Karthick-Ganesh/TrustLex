\begin{abstract}
LLM-integrated applications---support bots, retrieval-augmented assistants, agents---build each prompt by concatenating the developer's system prompt with outside text, so attacker-written text can pose as the developer (prompt injection). We present \TL{}, a domain-specific language and compiler that makes trust a grammar-level type. Inputs declare their origin; an exact, flow-sensitive analysis over a five-level lattice tracks trust through variables, interpolation and reassignment, and rejects any prompt in which outside free text can reach the system channel---even sanitized, since a sanitizer removes structure, not instructions---unless the input has a refinement type that cannot express an instruction or the developer declassifies it with a written reason. We prove that a program without declassification renders its system prompt independently of every free-text input, and that the check is complete. Accepted programs compile to sealed IR bound at run time into OpenAI or Anthropic payloads, with outside text sanitized, datamarked and explained to the model. \TL{} reaches an F1 of 1.00 on a labelled corpus (0.48 for a lexical linter) and removes all structural leakage (39.1\% to 0\%). On twelve popular open-source applications chosen by a pre-registered protocol, it finds outside text reaching the system prompt in eight, most often text the application's own model wrote. Live experiments on seven models with the Tensor Trust and Microsoft LLMail-Inject attack sets show that typed inputs block every attack written into them and that \TL{}'s layout gives the lowest indirect-injection success of every layout tested, including XML-tagged user turns (e.g.\ 34.5\% to 1.8\% on llama-3.1-8b with Tensor Trust attacks); replaying the leaking applications' layouts shows the fix helps in practice. A typical program compiles in about 2\,ms.
\end{abstract}

\section{Introduction}

Most real-world use of LLMs is an \emph{LLM-integrated application}: a company wraps a general-purpose model in its own logic---a support bot, a retrieval-augmented generation (RAG) assistant, an e-mail assistant or a tool-using agent---whose \emph{system prompt} (persona, business rules, restrictions) is combined at run time with outside text.

The application builds its prompt by concatenating strings: developer instructions, the customer's message, a retrieved document, a tool result. The model receives one token sequence and cannot reliably tell who wrote which part. An attacker who controls any outside text can therefore write text that \emph{looks like} developer instructions: \emph{direct} injection through the customer message~\cite{perez2022ignore}, or \emph{indirect} injection planted in a document, web page or API response that the application later retrieves~\cite{greshake2023indirect}. OWASP ranks prompt injection as the top risk for LLM applications~\cite{owasp2025}.

This resembles SQL injection, where queries were built by concatenating user input and the remedy was a change of \emph{construction}: prepared statements fix the query structure so that input can only fill typed slots. \TL{} applies this idea to the construction of prompts: untrusted text can fill a slot, and the compiler guarantees that free text never reaches the privileged system prompt---only a value of a validated type may, or text the developer explicitly declassifies with a written reason---and never forges message structure. The analogy is deliberately limited. A database parses the query before binding, so a bound value can never execute; an LLM reads every channel with the same attention mechanism and may still follow instructions inside data. \TL{} therefore guarantees \emph{where} untrusted text is placed, not how the model interprets it, and pairs this structural guarantee with spotlighting and with refinement types that remove free text altogether. Unlike model-level defences~\cite{wallace2024hierarchy,chen2025struq,hines2024spotlighting}, which depend on the model, and run-time detectors~\cite{jacob2024promptshield,rebedea2023nemo}, which add per-request cost without a guarantee, \TL{} acts at \emph{build time} and composes with both.

\textbf{Contributions.}
(1)~A prompt DSL in which trust is a grammar-level type, with explicit privileged and unprivileged channels, a sanitizer for the unprivileged channel, an audited declassification construct \code{declassify(e, "reason")}, and refinement types with a safety analysis for their patterns.
(2)~An exact, flow-sensitive security analysis with a non-interference theorem (the system prompt is independent of all free text unless declassified) and a completeness result, validated by property-based testing, and compiler-style diagnostics with taint paths and re-checked fix-its.
(3)~An end-to-end chain of custody from source to API payload: checksummed and HMAC-sealed IR that records every declassification, invariant re-checks, a named-sanitizer registry, and a run-time notice that tells the model what the data marking means.
(4)~An evaluation combining offline detection and leakage experiments, a pre-registered case study of twelve real open-source applications with proofs of concept, and live experiments on seven models in direct, retrieval and e-mail scenarios against industry-standard layouts, with the public Tensor Trust~\cite{toyer2024tensortrust} and LLMail-Inject~\cite{abdelnabi2025llmail} attack sets and a variant chosen on a separate development set.

\section{Threat Model and Scope}

\textbf{Parties.} The application developer writes the \TL{} program and is trusted. End-user messages are \lab{UNTRUSTED}. Retrieved documents and tool or API results are \lab{SEMI\_TRUSTED}: the store or service may contain attacker-planted text.

\textbf{Attacker.} The attacker controls the content of one or more inputs and knows the language, compiler and default sanitizer, but cannot modify the program, the compiler, or---when the HMAC seal is used---the compiled IR.

\textbf{Goal.} Untrusted text must not reach the developer's instructions: the rendered system prompt may depend on outside input only by choosing among a validated type's fixed values, or through a declassification the developer wrote and justified (Theorem~\ref{thm:ni}).

\textbf{Protecting API calls.} The compiler's output \emph{is} the API request body, so values enter it as JSON string data and a value such as \verb|"}]}, {"role": "system", ...| cannot forge a message; tool and API responses are \code{input r from tool} and cannot reach the system prompt; and the deployed artifact is checksummed and optionally HMAC-sealed, with the invariant re-checked by \code{bind()} before every call.

\textbf{Out of scope.} Persuasion inside the user turn, an agent's choice of tools (addressed by CaMeL~\cite{debenedetti2025camel}), and attacks on training or weights.

\section{The TrustLex Language}

Fig.~\ref{lst:example} shows a support bot for a telecom company. \code{var} declares developer text; \code{input} declares outside data with its source (\code{user} by default, \code{rag}, \code{tool}); an input may carry a refinement type. \code{system\{\dots\}} is the privileged system prompt and \code{instruction\{\dots\}} the user turn; blocks contain string literals and \code{insert(e)} items. Expressions are literals with \code{\{name\}} interpolation, names, concatenation \code{+}, \code{sanitize(e)}, \code{declassify(e, "reason")} and parentheses. Programs are straight-line: there are no branches, loops or calls. Unknown source tags fail closed.

\begin{figure}[t]
\begin{lstlisting}
var rules = "You are Ava, Acme Telecom support."
input msg                          # UNTRUSTED
input article from rag             # SEMI_TRUSTED
input order_id : pattern("[A-Z0-9]{8}")
input topic : enum("billing", "outage", "general")
system {
  insert(rules)
  "Order: {order_id}. Topic: {topic}."
}
instruction {
  "Help-center article:" insert(sanitize(article))
  "Customer message:"    insert(sanitize(msg))
}
\end{lstlisting}
\caption{A \TL{} program. Moving \code{insert(article)} into \code{system} is rejected with \code{TL-S011}; inserting \code{msg} there, with \code{TL-S010}.}
\label{lst:example}
\end{figure}

The grammar is LALR(1) with no conflicts:
{\small
\begin{align*}
\mathit{stmt} &::= \code{var}\ x = e \mid x = e \mid \mathit{block}\\
 &\mid\ \code{input}\ x\ [\code{from}\ s]\ [\code{:}\ \tau]\\
\mathit{block} &::= (\code{system} \mid \code{instruction})\\
 &\phantom{::=}\ \code{\{}\ (\mathit{str} \mid \code{insert(}e\code{)})^{*}\ \code{\}}\\
e &::= \mathit{str} \mid x \mid e + e \mid \code{sanitize(}e\code{)} \mid (e)\\
 &\mid\ \code{declassify(}e\code{,}\ \mathit{str}\code{)}
\end{align*}}

\textbf{Core typing rule.} \emph{Data from an \code{input} may enter a \code{system} block only if the input is validated or the developer declassifies it}---directly, by interpolation, or through any chain of variables and reassignments. \code{sanitize()} is not enough: it removes structure, not natural-language instructions, so sanitized free text in \code{system} is an error (\code{TL-S013}). Outside text may always enter \code{instruction} blocks. \code{declassify(e, "reason")} (e.g.\ to greet a customer by name) sanitizes $e$, requires a real reason (\code{TODO} is rejected), and is reported as a warning quoting the reason (\code{TL-W004}), or an error under \code{--no-declassify}.

\section{Security Type System}\label{sec:types}

\subsection{Trust lattice and clearances}
Labels form the chain
\begin{gather*}
\lab{TRUSTED} \sqsubseteq \lab{VALIDATED} \sqsubseteq \lab{SANITIZED}\\
\sqsubseteq \lab{SEMI\_TRUSTED} \sqsubseteq \lab{UNTRUSTED},
\end{gather*}
ordered by taint, with join $\sqcup$ the less trusted level. Literals are \lab{TRUSTED}; typed inputs \lab{VALIDATED}; user inputs \lab{UNTRUSTED}; \code{rag}/\code{tool} inputs \lab{SEMI\_TRUSTED}; $\mathit{label}(a+b) = \mathit{label}(a)\sqcup\mathit{label}(b)$, likewise for interpolation; \code{sanitize(e)} lowers every external part of $e$ to \lab{SANITIZED}. Content may enter a block only if its label is below the block's clearance---\lab{VALIDATED} for \code{system}, \lab{UNTRUSTED} (anything) for \code{instruction}---or it was declassified. Table~\ref{tab:levels} lists what each level admits; \lab{SEMI\_TRUSTED} and \lab{UNTRUSTED} differ under a relaxed policy that only warns about rag/tool data in \code{system}.

\subsection{Typing rules}
Fig.~\ref{fig:rules} gives the rules for labels. The environment $\Gamma$ maps names to labels and is threaded through statements ($\Gamma \vdash s \dashv \Gamma'$), which makes the analysis flow-sensitive; $\mathit{src}(\code{user}) = \lab{UNTRUSTED}$, $\mathit{src}(\code{rag}) = \mathit{src}(\code{tool}) = \lab{SEMI\_TRUSTED}$, and unknown sources map to \lab{UNTRUSTED}. \subsection{Exact flow-sensitive evaluation}
Instead of approximating, the checker evaluates the program symbolically. The value of each variable at each program point is a \emph{template}: literal text interleaved with input \emph{slots}, each recording whether it was sanitized and the path by which it arrived. Assignment is a strong update, so an overwritten variable is clean again (a flow-insensitive analysis would report a false positive); each block sees values at its own position; and partial sanitization such as \code{sanitize(u) + u} keeps a raw slot and is rejected.

\subsection{Refinement types and pattern safety}\label{sec:patterns}
A \code{pattern} validates only if it cannot match free text. The pattern is parsed with Python's regular-expression parser and its syntax tree walked; it is rejected (\code{TL-S012}) if it can match whitespace or invisible characters, uses \code{.} or a negated class, has an unbounded repeat, uses backreferences or lookarounds, or can match more than 64 characters. A value of an accepted type can select an option but cannot spell an instruction sentence. \code{bind()} checks every value against its type (\code{TL-G006}).

\subsection{Non-interference}
\begin{theorem}[Non-interference up to validation and declassification]\label{thm:ni}
Let $P$ be a program with no errors under the strict policy, $\mathit{san}$ the runtime sanitizer, and $D$ the set of inputs that $P$ declassifies into \code{system} blocks. Let $\sigma_1,\sigma_2$ assign strings to the inputs of $P$ such that both bind ($\sigma_i(y)\in L(\tau)$ for every validated input $y{:}\tau$). If $\sigma_1(y)=\sigma_2(y)$ for every validated input $y$ and $\mathit{san}(\sigma_1(x)) = \mathit{san}(\sigma_2(x))$ for every $x\in D$, then every \code{system} block of $P$ renders to the same text under $\sigma_1$ and $\sigma_2$. In particular, if $D=\emptyset$, the \code{system} blocks do not depend on any free-text input.
\end{theorem}

\begin{IEEEproof}[Proof sketch]
(1)~\emph{Exactness}: by induction over statements, the template bound to each variable denotes its runtime value; literals and inputs are base cases, concatenation, interpolation, \code{sanitize} and \code{declassify} are homomorphic over rendering, and assignment is an exact strong update because $P$ has no control flow. (2)~\emph{Admitted slots}: the block check admits a slot into \code{system} only if its input is validated or the slot is declassified, and hence sanitized; so $\mathit{render}(t,\sigma)$ depends on $\sigma$ only through $\sigma$ on validated inputs and $\mathit{san}\circ\sigma$ on inputs in $D$, which agree by assumption. (3)~By (1) the template of every \code{system} item is its runtime content, and by (2) that content is equal under $\sigma_1$ and $\sigma_2$.
\end{IEEEproof}

\textbf{Completeness.} Because evaluation is exact, a rejected program has a free-text slot that is not declassified in \code{system}, and two assignments differing only on that input render it differently: the check has no false positives. \textbf{Preservation.} IR slots come from the checked templates; \code{generate()}, \code{from\_json()} and \code{bind()} re-verify the invariant from each input's source tag or type rather than stored labels, and the optimizer rewrites only developer text. \textbf{Mechanised validation.} \textsc{Hypothesis} tests the theorem on random programs with typed inputs, sanitization and declassification, through IR serialization and every optimizer level (500 programs: 369 accepted, 131 rejected).

\textbf{Front end.} A PLY tokenizer records exact spans, seeds each token's trust and splits strings into text and \code{\{hole\}} parts, so diagnostics point at the leaking hole. The LALR(1) parser has error productions for targeted hints and computes exact ``expected'' sets by simulating pending reductions. \textbf{Semantic analysis} resolves names with close-match hints, evaluates templates, checks patterns, reports taint paths as secondary locations, and offers fix-its that are applied one at a time and re-checked: first moving the item to an \code{instruction} block, then a declassification whose placeholder reason must be replaced before the program compiles:
\begin{lstlisting}[language={},basicstyle=\ttfamily\scriptsize]
error[TL-S010]: UNTRUSTED data from input `user_msg`
                reaches a `system` block
 --> prompt.tlx:5:12
5 |     insert(user_msg)
  |            ^~~~~~~~ raw input inserted here
  = help: move `insert(user_msg)` to the `instruction`
          block on line 8, where outside text is allowed
  = help: or, if this text must be in the system prompt:
          insert(declassify(user_msg, "TODO: ..."))
\end{lstlisting}
\textbf{IR and binding.} The IR keeps text and slots separate, is canonical JSON with a SHA-256 checksum and an optional HMAC-SHA256 seal, and is re-verified on generation. A rule-based optimizer rewrites developer text to a fixpoint, property-tested to keep the slot sequence (8--13\% shorter at \code{-O1}). Sanitizers are registered by name; the default normalizes Unicode, removes control, zero-width and bidi characters, defuses role markers and forged transcript turns, caps length, and \emph{spotlights}~\cite{hines2024spotlighting} the value in \code{<untrusted\_input>} delimiters it cannot close; the datamarking variant also replaces whitespace with a marker. Whenever marked data is present, \code{bind()} adds a fixed notice to the system prompt explaining the marking.

\section{Complexity Analysis}\label{sec:complexity}

Let $n$ be the program size, $S$ the largest template and $m$ the IR size. Lexing, parsing and name resolution are $O(n)$; the security analysis is $O(n\cdot S)$ over a constant-height lattice; IR generation and sealing are $O(m)$; the optimizer is $O(k\cdot m)$ with $k \le m$ rounds; binding is linear in $m$ plus the input length, and no analysis runs per request. Measured on a Ryzen laptop (Python 3.10, median of 5 runs), compile time grows from 1.8\,ms for 10 statements to 18.8\,ms for 100 and 1.60\,s for 5{,}000 (0.18--0.32\,ms per statement); the example compiles in about 1.6\,ms.

\textbf{Worst case.} $k$ repetitions of \code{a = a + a} build $2^k$ parts, so \TL{} caps a template at 10{,}000 inserted values and 4\,M characters (about four times the largest context window), rejects larger ones (\code{TL-S016}) and collapses them to their distinct slots, keeping every label; checking stays bounded (0.68\,s at $k{=}40$). Attackers supply values only at bind time and cannot trigger the blow-up.

\textbf{Layouts.}\label{sec:layouts} Each scenario is one application in every layout a developer might use: \textbf{A} outside text raw in the system prompt; \textbf{B} raw in the user turn (industry standard); \textbf{Bt} B in XML tags (best practice); \textbf{S} sanitized in the system prompt (accepted by earlier \TL{} versions, now \code{TL-S013}); \textbf{C} the \TL{} program; and, for direct injection, \textbf{D}: C plus two typed fields that the attacker also fills, so a field that rejects the attack blocks the request. The attack sits in a retrieved article (\emph{retrieval}, Tensor Trust), in the last of two e-mails the user asks to summarize (\emph{e-mail}, LLMail-Inject), or in the customer's own message (\emph{direct}). Tables~\ref{tab:indirect}--\ref{tab:replay} give the results.


\textbf{Findings.} (1)~\emph{\TL{}'s layout has the lowest indirect-injection success on every model.} Scored by Tensor Trust's own rule, it is significantly below the industry standard on llama-3.1-8b (34.5\% to 1.8\%) and mistral-7b (43.6\% to 24.8\%), and on the quota-limited runs of allam-2-7b (42.4\% to 14.4\%) and qwen3.8-27b (20.3\% to 0\%), all $p<0.001$; XML tags alone (Bt) recover little of the gain (29.7\% and 42.4\%). (2)~\emph{Fewer e-mails reach the attacker.} Under LLMail-Inject's rule---the agent actually sends the attacker an e-mail---\TL{} cuts success from 23.0\% to 0\% on gemma-4-26b, 32.0\% to 4.0\% on llama-3.1-8b and 61.5\% to 16.0\% on mistral-7b (all $p<0.001$), while tags do not help (15.5\% and 33.5\%). (3)~\emph{Sanitized text in the system prompt is not safe:} with Tensor Trust attacks S is the worst layout on gemma-4-26b (9.7\%) and above tagging on most models. (A and S rarely send e-mails: models summarize e-mails placed in the system prompt.) (4)~\emph{Typed inputs block every attack before any API call} (D, 0\% on every model); D measures one thing---attack text cannot enter a refinement-typed field---and an attacker who leaves the fields valid meets the same defence as C. In the direct scenario C is also lowest on llama-3.1-8b (4.8\% vs.\ 30.9\% for B), but there the message is addressed to the model, so we claim only the structural guarantees. (5)~\emph{Cost.} Datamarking lowers benign-task success on gemma-4-26b from 87.5\% to 77.5\% and on no other model by more than 2.5 points.


\textbf{Proof of concept on the real applications.} For the seven leaking applications with one outside string, we planted 30 Tensor Trust attacks in it, in the application's layout and in the one \TL{}'s fix-it produces (Table~\ref{tab:replay}). The fixed layout lowers pooled success on all three models: from 36.7\% to 20.3\% on llama-3.1-8b, from 9.5\% to 1.0\% on gemma-4-26b and from 59.5\% to 48.1\% on allam-2-7b (all $p<0.001$).

Three points stand out. First, unlike the keyword filter, \TL{} decides from where text is placed rather than what it says, so it has no false positives on benign inputs and its compile-time verdict cannot be evaded by rephrasing an attack. Second, our gains vary more than the figure Hines et al.\ report: on llama-3.1-8b datamarking almost removes retrieval attacks, while on mistral-7b and allam-2-7b about half still succeed, and Microsoft's adaptive LLMail-Inject attacks, written against defences of this kind, keep succeeding on small models. Prompt-level defences depend strongly on the model and the attacks. This is exactly why \TL{} pairs spotlighting with model-independent compile-time guarantees. Third, CaMeL and StruQ protect a different layer (agent tool calls and model weights) and compose with \TL{}: a \TL{} program can supply the trusted prompt of a CaMeL-style system or be sent to a StruQ-trained model.

\subsection{Guidance for developers}
The results suggest a layered use of \TL{}. (1)~Give every input whose values can be enumerated or bounded a refinement type: such inputs blocked every attack on every model before any request. (2)~Keep customer messages and retrieved documents in the \code{instruction} channel, sanitized and datamarked; this layout had the lowest indirect-injection success on every model, and tagging alone recovers little of it. (3)~Use \code{declassify()} only for short values such as a customer's name, and review the reasons the compiler reports; treat everything a model wrote (memory, summaries) as outside text, as the case study shows it is the most overlooked source. (4)~Send the compiled prompt to a model trained to respect the instruction hierarchy~\cite{wallace2024hierarchy}, since the remaining risk lies in persuasion within the user turn, which no prompt-construction discipline can remove.

\section{Limitations and Threats to Validity}

The guarantee covers the privileged channel: untrusted text is still allowed, delimited, in the user turn, where a model can be persuaded, and declassification remains possible, visibly. Validation is syntactic (\code{[A-Za-z]\{1,40\}} admits one word), and completeness relies on straight-line programs. The public attack sets were written against other targets (a game, one e-mail agent). The models are small or mid-sized open-weight ones, and some free-tier runs are partial. Our own attacks are scored by a model-based judge validated on a sample; the public sets by their own rules. Each layout is one hand-written application, and the replay plants attacks in an application's outside text, not a full deployment. The case study models each application's main prompt path by hand, on open-source projects rather than proprietary deployments; two of four planned independent translations were done.

\section{Conclusion}

Prompt injection in LLM-integrated applications is in part a construction problem: trusted instructions and untrusted data are concatenated into one string. \TL{} borrows the remedy applied to SQL injection and cross-site scripting: the trust of every piece of text is part of the program's type, and unsafe prompts are not built. Its exact analysis yields non-interference for the privileged channel with no false positives, and its compiled output carries the guarantee to the API call. The experiments show the layers working together: refinement types block attacks independently of the model, channel separation keeps untrusted text out of the system prompt, and datamarked spotlighting gives the lowest indirect-injection success of every layout on seven models, though adaptive attacks still succeed against small ones. On twelve real applications, the compiler finds outside text in the system prompt of eight, most often text the application's own model wrote. Future work, motivated by the case study, includes control flow with sound joins and implicit-flow tracking, trust propagation through model calls in multi-step agent pipelines, integration with capability-based runtimes, and a language server for live diagnostics.
