\begin{abstract}
Companies increasingly deploy large language models (LLMs) inside their own applications: support bots on websites, retrieval-augmented assistants over internal documents, and agents that consume tool and API results. Each application builds its prompt by concatenating the developer's trusted system prompt with untrusted text, so attacker-controlled text can impersonate the developer (prompt injection). We present \TL{}, a domain-specific language and compiler that makes trust a grammar-level type. Inputs declare their origin; the compiler tracks trust through variables, interpolation, concatenation and reassignment by exact symbolic evaluation over a five-level lattice, and refuses to compile any prompt in which outside free text can reach the privileged system channel---even sanitized, since a sanitizer removes structure, not instructions---unless the input carries a refinement type that provably cannot express an instruction, or the developer declassifies it explicitly with a written reason that the compiler reports and the sealed artifact records. We prove that a program without declassification renders its system prompt independently of every free-text input, and that the check is complete for the language. Accepted programs compile to a checksummed, optionally HMAC-sealed intermediate representation that is bound at run time into OpenAI or Anthropic API payloads. On a labelled corpus \TL{} reaches an F1 score of 1.00 versus 0.48 for a lexical linter and 0.83 for a keyword filter; across 1{,}728 program--attack pairs it reduces structural leakage into the system prompt from 39.1\% to 0\%. Applied to twelve popular open-source LLM applications selected by a pre-registered protocol, it finds outside text reaching the system prompt in eight of them---retrieved documents, project files, skill descriptions and, most often overlooked, text the application's own model wrote---with no false positive on the other four. In live experiments with three hosted models, using our own attacks and the public Tensor Trust benchmark, typed inputs block 100\% of the attacks written into them before any API call, and \TL{}'s layout significantly lowers indirect-injection success relative to placing the document in the user turn (e.g.\ from 73.0\% to 56.2\% on allam-2-7b with Tensor Trust attacks, $p=0.013$). Compiling a typical program takes about 2\,ms. The implementation, evaluation harness and results are publicly available as an open-source artifact.
\end{abstract}

\section{Introduction}

Most real-world use of LLMs is not a person chatting with a model but an \emph{LLM-integrated application}: a company calls a general-purpose model through an API and wraps it in its own logic---a customer-support bot, a retrieval-augmented generation (RAG) assistant, an email assistant, or an agent that calls tools and web APIs. The model is not custom; the \emph{application} is. What makes it specific is its \emph{system prompt}---persona, business rules, restrictions---combined at run time with outside text.

The application builds its prompt by concatenating strings: developer instructions, the customer's message, a retrieved document, a tool result. The model receives one token sequence and cannot reliably tell who wrote which part. An attacker who controls any outside text can therefore write text that \emph{looks like} developer instructions: \emph{direct} injection through the customer message~\cite{perez2022ignore}, or \emph{indirect} injection planted in a document, web page or API response that the application later retrieves~\cite{greshake2023indirect}. OWASP ranks prompt injection as the top risk for LLM applications~\cite{owasp2025}.

This resembles SQL injection, where queries were built by concatenating user input and the remedy was a change of \emph{construction}: prepared statements fix the query structure so that input can only fill typed slots. \TL{} applies this idea to the construction of prompts: untrusted text can fill a slot, and the compiler guarantees that free text never reaches the privileged system prompt---only a value of a validated type may, or text the developer explicitly declassifies with a written reason---and never forges message structure. The analogy is deliberately limited. A database parses the query before binding, so a bound value can never execute; an LLM reads every channel with the same attention mechanism and may still follow instructions inside data. \TL{} therefore guarantees \emph{where} untrusted text is placed, not how the model interprets it, and pairs this structural guarantee with spotlighting and with refinement types that remove free text altogether.

Existing defences act at the model, by training or prompting it to separate instructions from data~\cite{wallace2024hierarchy,chen2025struq,hines2024spotlighting}, or at run time, through classifiers and guardrails~\cite{jacob2024promptshield,rebedea2023nemo}. The former depend on the model; the latter add per-request cost and give no guarantee. \TL{} acts at \emph{build time}, before the prompt exists, and composes with both.

\textbf{Contributions.}
(1)~A prompt DSL in which trust is a grammar-level type, with explicit privileged and unprivileged channels, a sanitizer for the unprivileged channel, an audited declassification construct \code{declassify(e, "reason")}, and refinement types with a safety analysis for their patterns.
(2)~An exact, flow-sensitive security analysis with a non-interference theorem (the system prompt is independent of all free text unless declassified) and a completeness result, validated by property-based testing, and compiler-style diagnostics with taint paths and re-checked fix-its.
(3)~An end-to-end chain of custody from source to API payload: checksummed and HMAC-sealed IR that records every declassification, invariant re-checks, a named-sanitizer registry, and a run-time notice that tells the model what the data marking means.
(4)~An evaluation combining offline detection and leakage experiments, a pre-registered case study of twelve real open-source applications, live attack-success experiments in direct and indirect scenarios against industry-standard layouts with our attacks and the public Tensor Trust benchmark~\cite{toyer2024tensortrust}, and a complexity analysis.

\TL{} designs the language so the analysis is exact. \textbf{Run-time detectors}~\cite{jacob2024promptshield,rebedea2023nemo} are probabilistic and add per-request cost; a detector can be registered as a named \TL{} sanitizer. \textbf{Auto-sanitizing templates}: CSAS~\cite{samuel2011csas}, the closest prior work, uses type qualifiers to insert context-appropriate sanitizers into web templates at compile time; \TL{} supplies the structural separation they assume. \textbf{Benchmarks}~\cite{toyer2024tensortrust,liu2024formalizing} evaluate attacks and defences at the model level. \textbf{Foundations}: lattice-based information flow~\cite{denning1976lattice}, non-interference~\cite{goguen1982security}, security type systems~\cite{volpano1996sound,sabelfeld2003language}, flow-sensitive typing~\cite{hunt2006flow} and declassification~\cite{sabelfeld2009declassification}; \code{declassify()} follows the ``what is released, where, and why'' dimensions of the latter by naming the value, fixing the block and requiring a reason.

\section{Threat Model and Scope}

\textbf{Parties.} The application developer writes the \TL{} program and is trusted. End-user messages are \lab{UNTRUSTED}. Retrieved documents and tool or API results are \lab{SEMI\_TRUSTED}: the store or service may contain attacker-planted text.

\textbf{Attacker.} The attacker controls the content of one or more inputs and knows the language, compiler and default sanitizer, but cannot modify the program, the compiler, or---when the HMAC seal is used---the compiled IR.

\textbf{Goal.} Untrusted text must not reach the developer's instructions: the rendered system prompt may depend on outside input only by choosing among a validated type's fixed values, or through a declassification the developer wrote and justified (Theorem~\ref{thm:ni}).

\textbf{Protecting API calls.} \TL{} protects the model API call at three points. (i)~The compiler's output \emph{is} the API request body; values enter it as JSON string data, never by splicing, so a value such as \verb|"}]}, {"role": "system", ...| stays inside its own field and cannot forge a message or role. (ii)~Responses from external APIs and tools are declared \code{input r from tool} and cannot reach the system prompt, covering indirect injection through API responses and search results. (iii)~The deployed prompt artifact is checksummed and optionally HMAC-sealed, and \code{bind()} re-checks the security invariant before every call, so a reviewed prompt cannot be silently weakened in production.

\textbf{Out of scope.} Persuasion inside the user turn (untrusted text is allowed there, delimited); which tools an agent decides to call, which capability-based runtimes such as CaMeL~\cite{debenedetti2025camel} address; and attacks on model training or weights.

\section{The TrustLex Language}

Fig.~\ref{lst:example} shows a support bot for a telecom company. \code{var} declares developer text; \code{input} declares outside data with its source (\code{user} by default, \code{rag}, \code{tool}); an input may carry a refinement type. \code{system\{\dots\}} is the privileged system prompt and \code{instruction\{\dots\}} the user turn; blocks contain string literals and \code{insert(e)} items. Expressions are literals with \code{\{name\}} interpolation, names, concatenation \code{+}, \code{sanitize(e)}, \code{declassify(e, "reason")} and parentheses. Programs are straight-line: there are no branches, loops or calls. Unknown source tags fail closed.

\begin{figure}[t]
\begin{lstlisting}
var rules = "You are Ava, Acme Telecom support."
input msg                          # UNTRUSTED
input article from rag             # SEMI_TRUSTED
input order_id : pattern("[A-Z0-9]{8}")
input topic : enum("billing", "outage", "general")
system {
  insert(rules)
  "Order: {order_id}. Topic: {topic}."
}
instruction {
  "Help-center article:" insert(sanitize(article))
  "Customer message:"    insert(sanitize(msg))
}
\end{lstlisting}
\caption{A \TL{} program. Moving \code{insert(article)} into \code{system} is rejected with \code{TL-S011}; inserting \code{msg} there, with \code{TL-S010}.}
\label{lst:example}
\end{figure}

The grammar is LALR(1) with no conflicts:
{\small
\begin{align*}
\mathit{stmt} &::= \code{var}\ x = e \mid x = e \mid \mathit{block}\\
 &\mid\ \code{input}\ x\ [\code{from}\ s]\ [\code{:}\ \tau]\\
\mathit{block} &::= (\code{system} \mid \code{instruction})\\
 &\phantom{::=}\ \code{\{}\ (\mathit{str} \mid \code{insert(}e\code{)})^{*}\ \code{\}}\\
e &::= \mathit{str} \mid x \mid e + e \mid \code{sanitize(}e\code{)} \mid (e)\\
 &\mid\ \code{declassify(}e\code{,}\ \mathit{str}\code{)}
\end{align*}}

\textbf{Core typing rule.} \emph{Data from an \code{input} may enter a \code{system} block only if the input is validated, or if the developer declassifies it}---however it gets there: directly, by interpolation, or through any chain of variables and reassignments. \code{sanitize()} alone is not enough: it removes structure (role markers, control characters, delimiter break-outs) but not natural-language instructions, so sanitized free text in \code{system} is an error (\code{TL-S013}). Untrusted data may always enter \code{instruction} blocks, where the runtime sanitizes or delimits it; this is the recommended layout, evaluated below as condition~C. \code{declassify(e, "reason")} is the explicit, audited exception (e.g.\ to greet a customer by name): it sanitizes $e$, requires a non-empty reason (a placeholder such as \code{TODO} is rejected), and every declassification into \code{system} is reported as a warning quoting the reason (\code{TL-W004}), or as an error under \code{--no-declassify} (\code{TL-S014}).

\section{Security Type System}\label{sec:types}

\subsection{Trust lattice and clearances}
Labels form the chain
\begin{gather*}
\lab{TRUSTED} \sqsubseteq \lab{VALIDATED} \sqsubseteq \lab{SANITIZED}\\
\sqsubseteq \lab{SEMI\_TRUSTED} \sqsubseteq \lab{UNTRUSTED},
\end{gather*}
ordered by taint, with join $\sqcup$ the less trusted level. Literals are \lab{TRUSTED}; typed inputs \lab{VALIDATED}; user inputs \lab{UNTRUSTED}; \code{rag}/\code{tool} inputs \lab{SEMI\_TRUSTED}; $\mathit{label}(a+b) = \mathit{label}(a)\sqcup\mathit{label}(b)$, likewise for interpolation; \code{sanitize(e)} lowers every external part of $e$ to \lab{SANITIZED}. Content may enter a block only if its label is below the block's clearance---\lab{VALIDATED} for \code{system}, \lab{UNTRUSTED} (anything) for \code{instruction}---or it was declassified. Each level has an operational role: \lab{VALIDATED} is the only outside data the privileged channel accepts and is type-checked at bind time; \lab{SANITIZED} is free text cleaned for the unprivileged channel, rejected in \code{system} unless declassified; and \lab{SEMI\_TRUSTED} and \lab{UNTRUSTED} differ under a relaxed policy that downgrades rag/tool data in \code{system} to a warning. Table~\ref{tab:levels} lists what each level admits.

\subsection{Typing rules}
Fig.~\ref{fig:rules} gives the rules for labels. The environment $\Gamma$ maps names to labels and is threaded through statements ($\Gamma \vdash s \dashv \Gamma'$), which makes the analysis flow-sensitive; $\mathit{src}(\code{user}) = \lab{UNTRUSTED}$, $\mathit{src}(\code{rag}) = \mathit{src}(\code{tool}) = \lab{SEMI\_TRUSTED}$, and unknown sources map to \lab{UNTRUSTED}. Interpolation desugars to concatenation, and \code{var} is assignment to a fresh name. Because the lattice is a chain, meet distributes over join, so (\textsc{San}) agrees with lowering each external part of $e$ to \lab{SANITIZED}. A judgement $\Gamma\vdash e:\ell,D$ also carries the set $D$ of inputs whose slots in $e$ were declassified; (\textsc{Dec}) adds them, every other rule takes the union of its premises' sets (omitted from the figure), and (\textsc{Sys}) admits an item whose free-text slots all come from $D$.

\subsection{Exact flow-sensitive evaluation}
Instead of approximating, the checker evaluates the program symbolically. The value of each variable at each program point is a \emph{template}: literal text interleaved with input \emph{slots}, each recording whether it was sanitized and the path by which it arrived. Assignment is a strong update, so an overwritten variable is clean again (a flow-insensitive analysis would report a false positive); each block sees values at its own position; and partial sanitization such as \code{sanitize(u) + u} keeps a raw slot and is rejected.

\subsection{Refinement types and pattern safety}\label{sec:patterns}
A \code{pattern} validates only if it cannot match free text. The pattern is parsed with Python's regular-expression parser and its syntax tree walked; it is rejected (\code{TL-S012}) if it can match whitespace or invisible characters, uses \code{.} or a negated class, has an unbounded repeat, uses backreferences or lookarounds, or can match more than 64 characters. A value of an accepted type can select an option but cannot spell an instruction sentence. \code{bind()} checks every value against its type (\code{TL-G006}).

\subsection{Non-interference}
\begin{theorem}[Non-interference up to validation and declassification]\label{thm:ni}
Let $P$ be a program with no errors under the strict policy, $\mathit{san}$ the runtime sanitizer, and $D$ the set of inputs that $P$ declassifies into \code{system} blocks. Let $\sigma_1,\sigma_2$ assign strings to the inputs of $P$ such that both bind ($\sigma_i(y)\in L(\tau)$ for every validated input $y{:}\tau$). If $\sigma_1(y)=\sigma_2(y)$ for every validated input $y$ and $\mathit{san}(\sigma_1(x)) = \mathit{san}(\sigma_2(x))$ for every $x\in D$, then every \code{system} block of $P$ renders to the same text under $\sigma_1$ and $\sigma_2$. In particular, if $D=\emptyset$, the \code{system} blocks do not depend on any free-text input.
\end{theorem}

\begin{IEEEproof}[Proof sketch]
(1)~\emph{Exactness}: by induction over statements, the template bound to each variable denotes its runtime value; literals and inputs are base cases, concatenation, interpolation, \code{sanitize} and \code{declassify} are homomorphic over rendering, and assignment is an exact strong update because $P$ has no control flow. (2)~\emph{Admitted slots}: the block check admits a slot into \code{system} only if its input is validated or the slot is declassified, and hence sanitized; so $\mathit{render}(t,\sigma)$ depends on $\sigma$ only through $\sigma$ on validated inputs and $\mathit{san}\circ\sigma$ on inputs in $D$, which agree by assumption. (3)~By (1) the template of every \code{system} item is its runtime content, and by (2) that content is equal under $\sigma_1$ and $\sigma_2$.
\end{IEEEproof}

\textbf{Completeness.} Because evaluation is exact, a program is rejected only if a slot of a free-text input that is not declassified reaches \code{system}, raw or sanitized, and then assignments as above that differ on that input render it differently: the check has no false positives. \textbf{Preservation.} IR slots come directly from the checked templates and carry each declassification's reason; \code{generate()}, \code{from\_json()} and \code{bind()} re-verify the invariant (a sanitized slot in a system message must be declassified), re-deriving each input's trust from its source tag or type rather than trusting stored labels; the optimizer rewrites only developer text. \textbf{Mechanised validation.} The theorem is tested with \textsc{Hypothesis} on random programs with typed inputs, sanitization and declassification: accepted programs render identical system text when non-declassified free text differs arbitrarily, rejected ones render differently, and both hold through IR serialization and every optimizer level (in a 500-program sample, 369 accepted and 131 rejected).

\textbf{Lexical analysis.} A PLY tokenizer records exact spans and seeds each token's intrinsic trust (literals \lab{TRUSTED}, names after \code{input} by source). Strings are split during lexing into text and \code{\{hole\}} parts, so later phases can point at the exact leaking hole. \textbf{Syntax analysis.} An LALR(1) grammar with error productions gives targeted hints (e.g.\ a bare variable in a block suggests \code{insert(x)}). Because LALR state merging over-reports acceptable tokens, the parser computes exact ``expected'' sets by simulating pending reductions per candidate token. \textbf{Semantic analysis.} Name resolution with close-match hints, the trust lattice, symbolic evaluation, pattern analysis, taint paths reported as secondary source locations, and machine-applicable fix-its, applied one at a time and re-checked after each. The first fix moves the offending item to the next \code{instruction} block (or a new one); declassification is offered second, with a placeholder reason that the developer must replace before the program compiles:
\begin{lstlisting}[language={},basicstyle=\ttfamily\scriptsize]
error[TL-S010]: UNTRUSTED data from input `user_msg`
                reaches a `system` block
 --> prompt.tlx:5:12
5 |     insert(user_msg)
  |            ^~~~~~~~ raw input inserted here
  = help: move `insert(user_msg)` to the `instruction`
          block on line 8, where outside text is allowed
  = help: or, if this text must be in the system prompt:
          insert(declassify(user_msg, "TODO: ..."))
\end{lstlisting}
\textbf{Intermediate code.} The IR keeps text parts and input slots separate, is canonical JSON with a SHA-256 checksum, and can carry an HMAC-SHA256 seal; \code{generate()} re-verifies its own output. \textbf{Optimization.} Rule-based rewriting of developer text to a fixpoint, with correctness defined as whitespace equivalence with the slot sequence preserved and property-tested (idempotent, never grows, keeps the invariant); at \code{-O1} the example shrinks by 8--13\%. \textbf{Binding.} A registry of named sanitizers; the default performs NFKC normalization, removes control, zero-width and bidi characters, defuses chat-template role markers, caps length, and \emph{spotlights}~\cite{hines2024spotlighting} the value in \code{<untrusted\_input>} delimiters it cannot close early; a \emph{datamarking} variant also replaces every whitespace run with a marker character. Spotlighting has two halves---marking the data and telling the model what the marking means---so whenever a prompt contains marked data, \code{bind()} adds a fixed, developer-trusted notice to the system prompt explaining the delimiters (sealed in the IR as an option).

\section{Complexity Analysis}\label{sec:complexity}

Let $n$ be the program size, $S$ the largest template built, and $m$ the IR size. Lexing and LALR(1) parsing are $O(n)$; name resolution is $O(n)$ expected; the security analysis is $O(n\cdot S)$, since each statement copies at most $S$ template parts and joins are over a constant-height lattice; pattern analysis is linear in the pattern; IR generation, checksumming and sealing are $O(m)$; the optimizer is $O(k\cdot m)$ for $k$ fixpoint rounds, with $k\le m$ because every rewrite except one-time normalization strictly shortens the text; binding is linear in $m$ plus the input length. No flow analysis runs per request.

\textbf{Typical programs.} When no value is repeatedly duplicated, $S$ is bounded by the program text and scaling is near-linear. Measured on an AMD Ryzen laptop (Python 3.10, median of 5 runs), compile time grows from 1.8\,ms for 10 statements to 18.8\,ms for 100, 90\,ms for 500 and 1.60\,s for 5{,}000, i.e.\ 0.18--0.32\,ms per statement (log--log slope 1.15 for $n\ge100$); lexing and parsing take 68--80\% of the time. The example program compiles in about 1.6\,ms.

\textbf{Worst case.} Because templates are copied, $k$ repetitions of \code{a = a + a} build $2^k$ parts, and checking time would double with each statement. \TL{} therefore caps a template at 10{,}000 inserted values and 4\,M characters of text, about four times the largest context window; past the cap the program is rejected (\code{TL-S016}) and the template is collapsed to its distinct slots, which keeps every trust label. Checking then stays bounded: 30\,ms at $k{=}10$, 0.30\,s at $k{=}14$ where the cap is reached, and 0.68\,s at $k{=}40$, linear in the number of statements past the cap. Hash-consing templates into a DAG would remove the remaining copying. The blow-up is not reachable by an attacker: the program is written by the trusted developer, and attacker-controlled values enter only at bind time, whose cost is linear in their length.

\section{Evaluation}\label{sec:eval}

\subsection{Setup}
\textbf{Corpus:} 54 hand-written programs (32 unsafe, 22 safe) in 15 categories---including six that put sanitized text in \code{system} (unsafe since \code{TL-S013}) and ten that declassify it with a reason (safe, with a warning)---32 attacks in 8 categories (direct override, role tokens, nested role tokens, transcript forgery, delimiter escape, Unicode obfuscation, payload splitting, social engineering), and 40 benign customer questions. \textbf{Baselines:} B1, a lexical linter; B2, a keyword blocklist on the naively rendered prompt; and a naive string-concatenation renderer. \textbf{Live models} (free API tiers, temperature 0, at most 1{,}024 output tokens): \code{openai/gpt-oss-20b} and \code{allam-2-7b} (Groq) and \code{gemma-4-26b-a4b-it} (Google). \textbf{Public benchmark:} from the Tensor Trust hijacking set~\cite{toyer2024tensortrust} (776 human-written attacks) we keep the 206 distinct attacks that name the target phrase ``Access Granted'' within 800 characters, replace the phrase with our canary, and sample 64 with a fixed seed. \textbf{Judging:} each trial embeds a fresh random canary; an attack succeeds if the reply contains it in a sentence that is not a refusal. \textbf{Statistics:} Wilson 95\% intervals~\cite{wilson1927} and exact McNemar tests~\cite{mcnemar1947} on paired trials.

Eight of the twelve applications let outside text reach the system prompt (13 findings: nine \code{TL-S011}, three \code{TL-S013}, one \code{TL-S012}), and \TL{} reports nothing for the four safe ones. First, \emph{the leaks are not raw customer messages}---no application puts those in the system prompt---but text developers did not treat as input: retrieved documents, job ads, a cloned repository's files, skill descriptions and, in four cases, \emph{text the application's own model wrote} (memory or conversation summaries), which carries planted instructions forward. Second, three applications escape outside text and still place it in the system channel, the pattern \code{TL-S013} rejects. Third, the safe applications already build condition~C by hand (tags, a notice, outside text in the user turn), which \TL{} makes the default. Only 2 of the 31 inputs could be refinement-typed, so typed fields protect a small share of today's inputs; and every application needed constructs \TL{} lacks---loops over documents (6), optional sections (12) and model outputs that re-enter a prompt (6). The two translations put every outside text in the same block with the same treatment (3 of 3 placements) and agree on the leak verdict in both applications, but differ in every trust tag: the author tagged text by who chose it (the person running the tool), we by who wrote it (a job advertisement, a repository's files). Under the default policy the tag does not change the verdict, since both tags lie above the system clearance; it changes only the error code (\code{TL-S010} instead of \code{TL-S011}). Under a policy that only warns about retrieved text, it would. Our guide listed job advertisements and cloned files as third-party text but did not say that whoever supplies a text is not its author; we have added that rule.

\textbf{Findings.} (1)~\emph{Typed inputs block every attack on every model before any API call.} D's 0\% holds by construction and measures one thing: attack text cannot enter a refinement-typed field, whatever the model. An attacker who leaves the typed fields valid and attacks through the free-text message meets the same defence as C. (2)~\emph{The public attacks are stronger}: on allam-2-7b they succeed in 56--75\% of trials versus 41--59\% for ours, yet D still blocks all of them. (3)~\emph{\TL{}'s layout significantly reduces indirect injection.} With the attack in a retrieved document, C is significantly lower than both naive layouts on allam-2-7b for both attack sets (exact McNemar, A vs.\ C $p=0.043$ and $0.017$; B vs.\ C $p=0.029$ and $0.013$), and lower than the system-prompt layout on gpt-oss-20b with our attacks (28.1\% to 6.2\%, $p=0.016$). (5)~\emph{A strongly aligned model} (gemma-4) resists all conditions, so they cannot be separated. Utility on benign inputs stayed between 80\% and 100\% in every condition, and \TL{} conditions were never more than one request below the naive ones.

Three points stand out. First, unlike the keyword filter, \TL{} decides from where text is placed rather than what it says, so it has no false positives on benign inputs and its compile-time verdict cannot be evaded by rephrasing an attack. Second, our spotlighting gains are smaller than the figure Hines et al.\ report; their experiments use GPT-family models and their own spotlighting variants and attacks, while we use the default delimiting sanitizer with smaller open models and include the public Tensor Trust attacks, so the comparison illustrates how strongly prompt-level defences depend on the model and the attacks. This is exactly why \TL{} pairs spotlighting with model-independent compile-time guarantees. Third, CaMeL and StruQ protect a different layer (agent tool calls and model weights) and compose with \TL{}: a \TL{} program can supply the trusted prompt of a CaMeL-style system or be sent to a StruQ-trained model.

\subsection{Guidance for developers}
The results suggest a layered use of \TL{}. (1)~Give every input whose values can be enumerated or bounded a refinement type: such inputs blocked every attack on every model before any request. (2)~Keep customer messages and retrieved documents in the \code{instruction} channel, sanitized and spotlighted; this layout significantly reduced indirect injection on two of the three models. (3)~Use \code{declassify()} only for short values such as a customer's name, and review the reasons the compiler reports; treat everything a model wrote (memory, summaries) as outside text, as the case study shows it is the most overlooked source. (4)~Send the compiled prompt to a model trained to respect the instruction hierarchy~\cite{wallace2024hierarchy}, since the remaining risk lies in persuasion within the user turn, which no prompt-construction discipline can remove.

\section{Limitations and Threats to Validity}

The guarantee covers the privileged channel: untrusted text is still allowed, delimited, in the user turn, where a model can still be persuaded, and a developer can still declassify free text into \code{system}, visibly and with a reason. The sanitizer removes structural vectors but cannot neutralize natural-language instructions in general, which is why sanitized text is kept out of \code{system}. Validation is syntactic: a permissive pattern such as \code{[A-Za-z]\{1,40\}} admits a single word. Completeness relies on straight-line programs; with branches the analysis would stay sound but not complete. Templates are capped in size, so a program that builds a prompt beyond any context window is rejected rather than checked (Section~\ref{sec:complexity}). Our corpus and attacks are hand-written, which the Tensor Trust benchmark mitigates; that benchmark was written against the game's defences rather than our application, and attacks that spell the target phrase indirectly are excluded. We test three free-tier models with 32--64 attacks per condition (32 for gpt-oss-20b on indirect Tensor Trust attacks, owing to the provider's daily token quota), so intervals are wide; repeats at temperature 0 vary only the canary. Canary-based success is a proxy; a refusal-aware judge avoids counting refusals that quote the canary, and empty replies (gpt-oss reasoning that exhausted the output budget, or a provider's safety filter) count as unsuccessful attacks; they occur mostly in the naive condition~A, and excluding them moves no success rate by more than 4.5 points and changes no significance verdict. The case study translates each application by hand and models its main prompt path, resolving configuration conditionals to the common case; its twelve applications are popular open-source projects, not proprietary deployments, and the operator/attacker boundary we drew (an operator's own settings are trusted) is a judgement a different reader could draw differently.

\section{Conclusion}

Prompt injection in LLM-integrated applications is in part a construction problem: trusted instructions and untrusted data are concatenated into one string. \TL{} borrows the remedy that programming languages applied to SQL injection and cross-site scripting, making the trust of every piece of text part of the program's type and refusing to build an unsafe prompt, while acknowledging that, unlike a database engine, a model can still be persuaded by data it is shown. Its exact analysis yields non-interference for the privileged channel with no false positives, and its compiled output carries the guarantee to the API call. The experiments show the layers working together: refinement types block attacks independently of the model, channel separation keeps untrusted text out of the system prompt, and spotlighting adds a model-dependent reduction that is significant only for indirect injection. On twelve real applications, the compiler finds outside text in the system prompt of eight, most often text the application's own model wrote. Future work, motivated by the case study, includes control flow with sound joins and implicit-flow tracking, trust propagation through model calls in multi-step agent pipelines, DAG-shared templates, integration with capability-based runtimes, and a language server for live diagnostics.
